## 0. What changed conceptually (read this first)

### ⚠️ Promoters and suppliers are ONE role
The single biggest change. Yakov: *"there should be no differentiation between
suppliers and promoters. They are one and the same. promoters can create
private events on the app or they can create public offers/events."*

The old model — supplier accounts (owning a `partner_brand`) get a different
app experience, detected via `GET /api/offers/me` (was `/api/supplier/me`) —
**is gone**:

- `RootView.MainTabs` no longer branches. **Every** account gets Tonight /
  Guestlist / **Stats** / You. (This reverted the earlier "hide Earnings for
  suppliers" requirement — superseded. The Earnings tab later became **Stats**,
  with earnings as one section of it.)
- `SupplierHomeView`, `SupplierTonightView`, `SupplierYouView` **deleted**.
  `SupplierHomeModel` + `SupplierClubPicker` + `SupplierOfferSheet` +
  `SupplierOfferDetailSheet` survive as shared pieces.
- What differs is the **thing you create**, not the account:
  - **Private event** → `promoter_nights`/`promoter_series` + allocations, invite link.
  - **Public offer** → `partner_offers`, listed on the consumer app.
- `+` opens `CreateTypeChooser` (Private event vs Public offer). Private goes to
  the existing create form **including the "your usual club or a custom pin"
  location chooser** — supplier accounts used to be force-routed past it, which
  is what Yakov noticed.
- A promoter's `partner_brand` is **auto-provisioned on their first public
  offer** from their `promoter_profiles` (name/logo). No pre-linking.

> **Renamed:** these are now `/api/offers/**` — they were `/api/supplier/**`,
> which had become a misnomer (they're the public-offer routes for *any*
> promoter). `/api/supplier/*` no longer exists. Safe to rename because the
> promoter app is v0.1.0 build 1 and has never been distributed; the released
> consumer app never called them.
>
> Still named for the old model (deliberately deferred — mechanical churn, no
> behaviour change): `src/lib/supplier-auth.ts` (`resolveSupplierBrand`), and
> the Swift `Supplier*` types (`SupplierRepo`, `SupplierOffer`,
> `SupplierHomeModel`, `SupplierOfferSheet`, …) under `Features/Supplier/`.

### ⚠️ `brand.is_active` no longer gates consumer visibility
`getActiveBrand()` does `.eq('is_active', true).maybeSingle()` — it assumes
**exactly one** active brand and **throws if two match**. So auto-provisioned
promoter brands are deliberately `is_active = false`.

That used to mean their offers would never appear. Fixed by making the consumer
feed aggregate: `getPartnerOffersByClub()` returns **every live offer across
every brand**, each carrying its own `brand`. **Visibility is the OFFER's
`is_active`, not its brand's** — every offer is already gated by review before a
live row exists. `brand.is_active` still marks the *primary* supplier
(`getActiveBrand`), which keeps `.maybeSingle()` safe.

**Do not activate a second brand.** It will 500 the consumer offers feed.

### ⚠️ Attribution is per-offer now, not app-wide
`RumbalistOffers.brand` (iOS) / `usePartner().brand` (web) are the *primary*
supplier only. Booking flow and offer cards brand themselves from
`offer.brand` / `offer.skipped_dates`. A venue can list offers from different
suppliers and each is credited correctly.

## 2. What we built this session

### Promoter review pipeline (phase 2)
- **Review badges** (Pending review / Rejected / Live) on the promoter's own
  nights + series, keyed on `review_status`.
- **Reject-with-reason**: portal prompts for a reason, stores
  `rejection_reason`, threads it back — shown inline on the rejected item and
  at the top of the edit form on resubmit.
- **Edit flow** for nights/series reusing the create sheet. Edits **re-enter
  review**, never write live. Nights go via `PATCH /api/promoter-nights/[id]`
  (service-role + allocation-ownership check; nights have no promoter UPDATE
  RLS policy). Series go direct via RLS. DB `rehold_*_edit` triggers enforce it
  server-side *and* block clients self-approving.
- **Per-night stats** in Earnings: joined/capacity, arrived, no-show, check-in
  rate — from `promoter_guests` (see §5 for why not bookings).

### Push (foundation only — NOT functional yet, see §4)
`PushManager` + AppDelegate register APNs, persist to `device_tokens`, route
`review_outcome` payloads to refresh screens. Backend `src/lib/push.ts` is an
env-gated APNs sender (HTTP/2 + ES256, no new deps). Portal review outcomes call
`notify()` + `sendPushToUser()`.

### Box detail sheets ("tap any box")
Tapping any night/series/offer opens a detail sheet: who's coming, party sizes,
arrived, location-consent, stats + all actions (open list, edit, share, toggle
visibility, delete). Series sheets add a **skip-a-week** manager
(`promoter_series.skipped_dates`).

### Tonight, rebuilt
- Was answering *"is there a one-off night dated today?"*. Now answers *"what's
  running tonight?"* — **recurring series** (which materialize lazily, so
  they're invisible via `allocations`; a promoter whose only night was a weekly
  series saw an empty Tonight), **all** one-off nights today (was `.first`
  only), and public offers live tonight.
- **Grouped by venue**, not by type — offer rows carried no venue at all.

### Consumer: supplier branding restored
Rumba's pre-refactor look is back in checkout: pink `#FF2D92` accent, animated
gloss wordmark, "Club Fuoco · via 〈mark〉", mark on the free CTA, and the
**Miami-pink Apple Wallet pass** (`logo-rumbalist.png` restored). All
data-driven from `partner_brands`. **Scoped exception to the no-pink rule** —
see §6.

### Per-night offer deactivation (the newest feature)
`valid_days` = what an offer *normally* runs; `skipped_dates` = exceptions
("normally Monday, but not Monday the 20th").
- **Applies immediately, no review queue** — scheduling, not content. Someone
  cancelling this coming Monday can't wait 3 business days.
- `PATCH /api/offers/:id/nights { date, skipped }` — own route,
  ownership-checked, prunes past dates.
- App: "Deactivate Monday 20 July" names the selected chip; skipped chips render
  struck-through + OFF.
- **Server enforces**: `join-guestlist` refuses a claim on a skipped night
  (`offerRunsOn`). Client filtering is presentation only.
- Both consumer clients filter against `plan.date`.

### Earnings tab → **Stats** tab
`EarningsView` only read private-night allocations, so an offers-only account
(Rumba: 15 offers, 0 private nights) saw an empty page. Reframed as **Stats**
(`chart.bar` icon; entry-point struct still named `EarningsView`, model is
`StatisticsModel`):
- **Overview**: guests this month = private-night list names + offer bookings,
  combined; arrived; check-in rate.
- **Public offers** section: per-offer people + arrived, by venue.
- **Earnings** section, always visible: private-night payouts **+** offer
  revenue (paid VIP tables). Free guestlists correctly read €0.
- New **`GET /api/offers/stats`** (`brandOrNull`, so a brand-less promoter gets
  zeroes not a 403): rolls up `rumbalist_purchases` matched to the caller's
  offers by `venue_id`+`product_kind` (same scoping as the guests route), joins
  `bookings` for `party_size`/`checked_in_at`, sums `price_eur` → `revenue`.
  One server-side aggregate, not N per-offer calls. **Verified end-to-end** by
  minting a Rumba session (see §5 for the technique): correct data, clean Swift
  decode. Rumba's numbers are real (7 guests this month) but €0 earnings —
  all its bookings are Free Guestlist, and `arrived=0` because none have a
  `checked_in_at`. That's the data, not a bug.

### Consumer apps respect skipped offer nights
`/api/partner` returns `skipped_dates` per offer; both consumer clients (iOS
`ClubDetailView`, web venue page) filter offers against the planned night
(`plan.date`). Client filtering is presentation — `offerRunsOn` in
`join-guestlist` is the enforcement.

### Route rename + smaller
- **`/api/supplier/**` → `/api/offers/**`** (see §0). Verified live: new paths
  401, old paths 404.
- **Delete offer** re-wired into the app detail sheet (it silently vanished
  after the unification — the sheet only renders a row when its closure is
  non-nil). Both Deactivate (app + portal) and Delete (app) now confirm.
- **Tonight** uses the shared `FuocoHeader` (was a one-off "Hola, <name>" bar
  that also scrolled away, since it sat inside the ScrollView).
- Guestlist dropped a stray "No nights assigned yet" line — it only tested
  nights/series, so it fired while sitting on a full list of offers.

### Portal: Instagram verification + adjustment
Verification was only an implicit side-effect of Approve; a wrong handle meant
re-applying. Now: `PATCH /api/portal/promoters/:id { instagram?, ig_verified? }`
— a **Verify/Unverify** toggle + badge, and **Edit handle**. Approving with an
unverified IG warns explicitly. **Changing the handle clears `ig_verified`** —
the code was proved against the *old* account, so adjustment can't launder an
unverified account into a verified one. Audited as `promoter.instagram`.

### Smaller
- **Image loads**: Google Places URLs stored at `maxwidth=800` were ~5× oversized
  for cards. `CachedAsyncImage(targetWidth:)` rewrites `maxwidth`; one shared
  feed thumb width (220pt → one cache entry per photo across card types) +
  prefetch of the first ~18 covers. Heroes stay native.
- **Pacha → "Ku (formerly Pacha)"** — DB `clubs.name` (app reads it live) +
  marketing page. The 4am Places sync fetches `name` but **never writes it**, so
  it won't revert. Slug stays `pacha-barcelona` (links).
- **Confirmations** before Deactivate (app + portal) and Delete (app).
- `ValidDays.parse` — canonical picker strings matched exactly, legacy free-form
  fallback (every/any/daily, comma lists, dash/`to` ranges w/ wrap, weekends,
  full day names), 18 DEBUG launch self-checks.
- Location priming sheet: content-sized detent (was clipping "Not now"), icon
  moved onto the close row.

## 5. Traps / things learned the hard way

- **`bookings` / `rumbalist_purchases` have NO night linkage.** `bookings` joins
  by `club_id`+`booking_date`; `rumbalist_purchases` by `venue_id`+`event_date`
  (and has no `checked_in_at`). Matching by club+date would attribute other
  promoters' traffic. Per-night promoter stats therefore come from
  `promoter_guests.checked_in_at` — the only night-linked source. The original
  brief asked for bookings-based stats; that's not possible as the schema stands.
- **Series occurrences materialize lazily** (`ensureOccurrence` on link open), so
  a series has no night/allocation row until someone opens it. Anything that
  looks for "tonight" via `allocations` will miss series entirely.
- **`.maybeSingle()` on `is_active` brands** — see §0. Landmine.
- **Supplier writes are queued** (`pending_changes`), so they don't take effect
  until approved. Yakov "accidentally deactivated an offer" — it had actually
  been queued and never applied; the fix was discarding the pending row.
  **Portal writes are live** (no queue) — higher stakes.
- **`SupplierOfferDetailSheet` renders a row only if its closure is non-nil.**
  That's how Delete silently went missing after the unification.
- SwiftUI: `.fixedSize(horizontal:)` on a Text inside an HStack forces the row
  wider than the screen → the whole page pans horizontally. Bit us on the offer
  card.
- **"Not hooked up" is usually a stale build.** When a device screen looked
  wrong, twice the cause was the old binary still resident, not a code bug.
  Verify with `strings <app>/…​.debug.dylib | grep '<new copy>'`, and prefer a
  clean `devicectl device uninstall` + reinstall when in doubt (it clears the
  session, so the user must re-login).
- **Testing an auth-gated route as a specific user, non-destructively:** mint a
  session with the service key without touching the password —
  `POST /auth/v1/admin/generate_link {type:magiclink,email}` → take
  `hashed_token` → `POST /auth/v1/verify {type:magiclink,token_hash}` (with the
  **anon** key) → returns `access_token`. Used this to prove `/api/offers/stats`
  end-to-end as Rumba. And a `swift <file>.swift` one-off is the fastest way to
  confirm a `Decodable` shape against real JSON.
- **`rumbalist_purchases` price/attendance reality:** most rows are Free
  Guestlist (`price_eur = 0`) and have no `checked_in_at`, so revenue and
  "arrived" legitimately read 0. Not a wiring bug — the data is sparse.
